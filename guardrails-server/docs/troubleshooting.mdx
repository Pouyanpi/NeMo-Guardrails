Start with the failing phase: application startup, a request before response
headers, a stream after headers, or shutdown. Record the operation, selected
provider instance and dialect, HTTP status, and error code. For a stream, record
whether an error event followed the headers and whether any text had already
arrived. Use a minimal synthetic request when reproducing a failure; exclude
credentials and private request or response content from shared diagnostics.

## Startup fails or the embedded runtime is unavailable

From the directory containing your manifest, run:

```bash
guardrails-proxy validate proxy.yaml
guardrails-proxy inspect proxy.yaml
guardrails-proxy serve proxy.yaml
```

| Observation | Diagnosis and next step |
| --- | --- |
| `validate` fails | Read its error and check manifest fields, distinct mounts, upstream URL, and Rails paths. Relative Rails paths resolve against the manifest directory. |
| `validate` passes but `serve` fails | Inspect the startup exception. Rails contents, actions, model dependencies, and credentials are initialized only during startup. Every catalog entry loads, including unused entries. |
| An embedded request reports `The experimental proxy runtime is not available.` | Enter the proxy lifespan from the parent lifespan. Mounting the application alone does not initialize its owners. |
| Startup gets slower as the catalog grows | Account for every Rails ID in every replica. Different IDs create separate engines even when they use the same directory. |

`inspect` describes routes, profiles, and fixed Rails selections. It does not
execute checks or establish upstream compatibility. Compare its output with the
actual deployed manifest, then use the [embedding recipe](python-integration.mdx#lifespan-and-embedding)
if a parent application owns startup. Treat inspected deployment addresses as
operational metadata when sharing output.

## A request is rejected or a check fails

For the shipped OpenAI bindings, use the error code as well as the status:

| Symptom | What to check |
| --- | --- |
| HTTP 400, `content_blocked` | A configured rule blocked input or buffered output. Reproduce with known harmless input and the intended Rails configuration. A block alone does not indicate a detector failure. |
| HTTP 502, `config_resolution_failed` | A Python resolver failed or returned an invalid/unregistered ID. Check the trusted identity/state it uses and the preloaded catalog. Fixed per-provider IDs bypass the resolver. |
| HTTP 422, `unsupported_rail_types` | The selected configuration enables rail types unsupported by this path. Compare its input/output checks with the configuration described in the Python and provider guides. |
| HTTP 422, `unsupported_stream_inspection_policy` | With output checks enabled, configure streaming checks with `stream_first: false`. |
| HTTP 502, `guardrails_input_check_failed` or `guardrails_output_check_failed` | Checking could not complete. Inspect the checking service's dependencies, credentials, availability, and application-side diagnostics. The client error deliberately omits internal exception details. |
| HTTP 422 request-shape rejection or HTTP 502 response-shape rejection | Compare the payload with the selected operation and dialect's coverage. A valid upstream API payload may contain unsupported history, tools, generated content, or unknown fields. |
| HTTP 415 representation rejection | Check request media type and content encoding against the binding. Use the JSON request shown in the quickstart to isolate framing from content. |
| HTTP 422, `request_content_not_replaceable`, or HTTP 502, `response_content_not_replaceable` | A check requested replacement. Current integrations reject replacement outcomes. Choose checks compatible with allow/block behavior. |
| Upstream authentication or model error | Check destination credentials, upstream model ID, and routing. Inference credentials and optional checking-service credentials serve separate roles. |

The [error mapping](../src/guardrails_proxy/providers/openai/errors.py) defines
additional routing and size-limit codes. Unsupported content on a guarded route
does not fall back to pass-through. Conversely, unselected operations can pass
through without inspection: verify the route as well as the enabled Rails checks
when a request unexpectedly avoids blocking.

Use the [coverage table](providers-and-streaming.mdx#coverage-of-the-shipped-profiles)
and [contract exports](guard-contracts.mdx#inspect-a-contract) to identify a field
mismatch. Add a deliberate [binding extension](extend-provider-bindings.mdx) only
when you have established how the new field should be handled.

## Streaming is delayed or ends with an error

Reproduce with `curl -N -i` using the [streaming request](quickstart.mdx#request-a-stream-or-use-responses).
`-N` disables curl's output buffering; `-i` shows when response headers arrive.
If your deployment permits direct access, compare the same synthetic request
through the ingress and directly to the proxy to isolate gateway buffering.

| Observation | Diagnosis and next step |
| --- | --- |
| Headers arrive, but text waits until completion | Windows count nonempty provider text deltas. A response shorter than `chunk_size` waits for the final partial-window check. Check the Rails window size and ingress buffering. |
| Text arrives in batches | Each approved window releases its retained bytes. Smaller windows increase check frequency; measure latency and checking cost before changing them. |
| HTTP 200 followed by an SSE error | Headers were committed before the failure. Read the provider-shaped error event; HTTP success alone does not establish successful completion. |
| SSE error with type `unsupported_response` | Inspect a minimal reproduction for invalid SSE, unsupported events, inconsistent snapshots, missing terminal behavior, or event/pending-byte limits. The binding determines the error code. |
| `stream_processing_failed` | An unexpected stream-processing exception occurred. Inspect application-side diagnostics and custom hooks; this generic code does not identify the cause. |
| `upstream_stream_failed` | Investigate upstream body delivery and read/idle timeouts. Compare upstream and ingress behavior with the same request. |
| A late block follows visible text | Earlier approved windows cannot be retracted. Define how the application presents partial output and stream errors. |

The [offline fixture](quickstart.mdx#see-output-blocking-without-a-model) gives a
deterministic example of HTTP 200 followed by an output-blocking SSE error.
Accepted upstream headers do not validate the event body; even the first event
can fail after downstream headers are sent. See [streaming lifecycle](architecture-requests.mdx#streaming-errors-and-cleanup)
for release and cleanup ordering.

## A client disconnects or shutdown reports incomplete cleanup

Exercise disconnect behavior through the actual ingress using a stream long
enough to interrupt. Start the request with `curl -N`, interrupt it, and observe
the upstream connection and proxy cleanup diagnostics. An in-process ASGI test
cannot establish how sockets, ingress buffering, and disconnect propagation behave.
Do not assume that the fixed, short offline response is sufficient for this test.

These warning messages identify different cleanup owners:

| Warning prefix | Logger | Investigate |
| --- | --- | --- |
| `Stream cleanup timed out` or `Stream cleanup failed` | `guardrails_proxy._stream_cleanup` | The request's upstream iterator and response owner, including a custom transport's response stream. |
| `HTTP client cleanup timed out` or `HTTP client cleanup failed` | `guardrails_proxy._runtime` | The lifespan's shared client and its outbound transport. |
| `Guardrails cleanup timed out` or `Guardrails cleanup failed` | `guardrails_proxy.rails._repository` | Rails engines and their checking dependencies during rollback or shutdown. |

Each message ends with `resources may remain open.` Configure the host's Python
logging handlers to retain these warnings. A timeout means cleanup was not
confirmed; a finished HTTP response does not prove release. Cleanup attempts
are shielded and cooperatively bounded, so blocking or cancellation-suppressing
code can defeat the intended budget. Custom owners must support repeatable,
cancellation-cooperative closing.

Check resource behavior after repeated disconnects and shutdown, including open
connections and tasks owned by your transport or checking services. Keep network
read/idle timeouts separate from cleanup budgets; changing the manifest's
`timeout` is not a cleanup fix. Follow the [transport ownership reference](../src/guardrails_proxy/http-transport.md#constraints-and-ownership)
and [lifecycle validation requirements](../DEVELOPMENT.md#compatibility-and-lifecycle-validation)
when investigating a resource leak.
