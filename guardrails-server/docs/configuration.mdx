Configure where requests go and which checks apply in separate places. This lets
you reuse a Rails configuration across upstreams, or apply different checks to
the same provider operation.

| Configuration | Purpose |
| --- | --- |
| Proxy manifest or Python `ProxyConfig` | Select instances, upstreams, bound operations, dialects, and Rails IDs. |
| Rails directory | Define the input/output checks and their models, actions, and streaming settings. |
| Exported guard contract | Describe the selected binding's coverage for review. It is not loaded as runtime configuration. |

## Declare a deployment

```yaml
version: 1
rails_configs:
  - id: standard
    config_path: ./rails/standard
providers:
  - provider: openai
    instance_id: gateway
    base_url: https://gateway.example/v1
    mount_path: /gateway
    operations: [chat_completions, responses]
    dialect: litellm
    rails_config_id: standard
```

This mounts guarded operations at `/gateway/v1/chat/completions` and
`/gateway/v1/responses`, forwarding to the configured gateway. Remove `dialect`
to select the native bindings. The hostname does not determine compatibility.

`instance_id` is the application's identity for this deployment declaration;
`mount_path` determines how incoming requests reach it. A model name inside a
provider request is a separate value. See [deployment](deployment.mdx) for
multiple upstreams and one-route routing.

## Keep Rails configuration separate

Keep `proxy.yaml` outside every Rails directory. The library loads YAML files
from its Rails directory recursively; the deployment manifest and Rails YAML
are different formats.

Relative `config_path` values resolve against the manifest's directory. A
symlinked manifest uses its target directory. The manifest does not expand
`~` or environment-variable expressions. Declare credential-free upstream URLs
and manage authentication through request headers or an application transport.

Rails directories are trusted application code: their actions can execute
Python. They must not be accepted as caller-supplied uploads.

## Choose operations and dialects

| Field | Meaning |
| --- | --- |
| `provider` | Built-in protocol family; currently `openai`. |
| `instance_id` | Unique instance identity within the application. |
| `base_url` | Explicit HTTP(S) API base, without userinfo, query, or fragment. |
| `mount_path` | Optional unique local prefix; defaults to the root mount. |
| `operations` | Nonempty ordered selection of `chat_completions`, `responses`, or both. |
| `dialect` | Omit for native bindings; use `litellm` for the reviewed dialect. |
| `rails_config_id` | A declared Rails ID. Required for each provider in YAML. |

Unknown names and conflicting routes are rejected. There is no implicit addition
of future operations and no automatic dialect detection.

Operation selection installs guard bindings. It does not create an HTTP route
allowlist: unselected operations may still pass through. Enforce an inbound route
allowlist separately if your deployment needs one. Enabling a binding also does
not activate checks disabled in the selected Rails configuration.

## Share a Rails catalog

Declare each configuration once in `rails_configs`. Several providers can use
the same `rails_config_id`, or each can choose a different entry. YAML makes a
fixed selection per provider. Use [Python resolution](python-integration.mdx#select-rails-per-request)
when selection depends on authenticated request context or the operation.

A resolver selects one configuration, not a sequence of configurations. All
catalog entries initialize before application readiness, including unused ones.
Requests look up ready checkers; they do not load configuration files. An
initialization failure prevents readiness and triggers cleanup attempts.

Preloading increases startup work and resource use as you add configurations.
Different IDs create independent Rails owners even when they refer to the same
path. The catalog is fixed for an application lifespan; hot reload and dynamic
configuration discovery are not implemented by this interface.

## Inspect before serving

With the installed environment active, run from your deployment directory
(see the [quickstart](quickstart.mdx)):

```bash
guardrails-proxy validate proxy.yaml
guardrails-proxy inspect proxy.yaml
guardrails-proxy schema > proxy.schema.json
```

| Command | What it establishes |
| --- | --- |
| `validate` | Data, directory/config-file availability, URL rules, and route composition. It does not load Rails contents or contact providers. |
| `inspect` | JSON with effective routes, bound profiles, fixed Rails IDs, limits, and pass-through behavior. It does not report enabled checks or establish upstream compatibility. |
| `schema` | JSON Schema for the manifest, derived from its model. Semantic checks still require `validate`. |
| `serve` | Initializes resources and Rails, then serves the same assembled application. |

Inspection includes deployment metadata such as upstream addresses. Treat that
output according to your deployment's access policy.

## Set limits

The following optional manifest fields apply to the application:

| Field | Default | Purpose |
| --- | --- | --- |
| `path_prefix` | Empty | Prefix all provider mounts. |
| `max_request_body_bytes` | `1048576` | Bound guarded request bodies. |
| `max_response_body_bytes` | `10485760` | Bound inspected buffered responses and supply stream event/pending limits. |
| `timeout` | `30.0` seconds | Outbound HTTP timeout setting. |

These are not global upload or response limits for unrelated pass-through
operations. Stream limits are also not a complete process memory budget. Read
and idle timeouts are separate from cooperative cleanup budgets.

`serve` defaults to `127.0.0.1:8000`. Override with `--host` and `--port`.
Access logging and automatic forwarded-header trust are disabled by the launcher.

## Manifest validation rules

Use one UTF-8 YAML document with `version: 1`. The parser rejects duplicate keys,
unknown fields, explicit tags, aliases, anchors, merges, and non-string mapping
keys. It bounds the document to 1 MiB, depth 32, and 10,000 nodes including keys.
There are no callback imports or dynamic resolver expressions in YAML.

For Python path semantics and callbacks, see [Python integration](python-integration.mdx).
For the exact bound content coverage, see [providers and streaming](providers-and-streaming.mdx).
